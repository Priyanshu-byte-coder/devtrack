## GitHub rate limiting

All server GitHub calls use [github-request.ts](../../src/lib/github-request.ts). The transport coalesces identical read requests, caches successful credential-scoped responses, revalidates with ETags, serializes outbound work per credential within each Node process, and gives queue/network work a deadline. Primary cooldowns are separated into core/search/GraphQL resources; secondary cooldowns cover the credential. Retry-After seconds/dates, reset headers, 429 and GraphQL RATE_LIMITED responses are handled. Ordinary permission-denied 403s remain permission errors. Redirects are bounded and restricted to the same GitHub API authority so credentials cannot follow redirects elsewhere.

Redis shares response caches and cooldowns between instances when configured; memory is a bounded fallback. The queue and single-flight map are process-local, not a distributed lock. This reduces redundant traffic and respects exhausted quotas; it does not increase GitHub's quota. During a cooldown, routes return 429 and Retry-After immediately. Successful cached data can still be served. Search-backed list metrics explicitly identify incomplete results when the 1,000-result/page/time budget is reached. Exact goal and weekly totals use total_count instead of collecting every search result.

Configure Upstash Redis for shared caches/cooldowns and production AI quotas. Redis calls have deadlines and automatic retries disabled. Configure a stable 64-hex-character ENCRYPTION_KEY and sign in again after adoption so cron can use an encrypted primary OAuth token. Server session cookies retain the credential; public session JSON does not. GitHub's repo scope is retained for the existing private repository analytics feature; public profile searches explicitly select public activity.
